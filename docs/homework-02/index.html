01 From mnemonic to Ethereum address

A conventional externally owned account (EOA) starts with unpredictable entropy. The following ordered pipeline connects the six technologies in the assignment; the page explains these operations rather than executing wallet derivation.

  1. Secure entropy

    Secure randomness

    A cryptographically secure random source supplies 128, 160, 192, 224, or 256 initial bits. Unpredictability begins here: human-chosen phrases and ordinary pseudorandom generators are unsuitable sources for wallet creation.

  2. Mnemonic

    BIP-39

    The first ENT/32 bits of SHA-256(entropy) form a checksum. Appending it and splitting into 11-bit indices selects words from a 2048-word list. Thus 128 entropy bits + 4 checksum bits → 12 words. The extra bits provide redundancy, not randomness. BIP-39

  3. Seed

    BIP-39 · PBKDF2

    PBKDF2-HMAC-SHA512 uses 2048 iterations: the mnemonic is the password, and "mnemonic" + passphrase is the salt. Both are UTF-8 NFKD-normalized; an absent passphrase is empty. The output is 512 bits (64 bytes), whose unpredictability remains constrained by the original entropy and passphrase.

  4. Derived private key

    BIP-32 · BIP-44

    BIP-32 starts with HMAC-SHA512(key = "Bitcoin seed", data = seed). Its left 32 bytes give master scalar material and its right 32 bytes a chain code. A master scalar must satisfy 1 ≤ k < n, where n is the secp256k1 generator order. Child derivation combines a parent key, chain code, and index using HMAC-SHA512 and scalar arithmetic; it also checks for invalid results.

  5. Public key

    secp256k1

    Elliptic-curve scalar multiplication gives Q = kG: k is the derived private scalar, G the fixed generator, and Q the public point. This relationship supports ECDSA signing for conventional Ethereum EOAs. It is not hashing. Homework 01 explains scalar multiplication on a toy curve; real parameters are specified in SEC 2, §2.4.1.

  6. Ethereum address

    Keccak-256

    Serialize the uncompressed point's x and y coordinates as 32 big-endian bytes each, retaining leading zeros. Hash the 64-byte x || y, excluding the 0x04 point prefix, with Ethereum Keccak-256. The final 20 digest bytes become the address: 160 bits, 40 hexadecimal characters, or 42 with 0x. The input is binary coordinates, not their hexadecimal text. Yellow Paper, Appendix F

  7. Checksummed address

    EIP-55

    Hash the lowercase 40-character address's ASCII text, without 0x, using Keccak-256. Uppercase each a–f letter whose corresponding digest nibble is at least 8; otherwise retain lowercase. Digits stay unchanged. This differs from hashing public-key bytes: the purpose is transcription-error detection, and the underlying 20 bytes do not change. EIP-55

A path through the key tree

Hardened BIP-32 children require parent private-key material. Non-hardened child public keys can be derived from an extended public key, which includes the chain code. BIP-44 organizes this tree; it is a path convention, not another hash.

02 What each primitive does

On narrow screens, scroll the comparison table horizontally.

Different operations, different objectives
ConceptRolePipeline example
Key generationCreate unpredictable initial material with secure randomness.Initial entropy; a directly sampled valid private scalar is another approach.
Key derivationDeterministically transform existing secret material into keys.BIP-39 mnemonic → seed; BIP-32 seed/parent → child keys.
Public-key cryptographyConnect private/public keys and support signatures.secp256k1 scalar multiplication and ECDSA.
HashingMap data to a fixed-length digest.SHA-256 for mnemonic checksums; SHA-512 within HMAC/PBKDF2; Keccak-256 for addresses.
ChecksumsDetect some representation errors.BIP-39 checksum bits and EIP-55 letter case.
EncodingRepresent information in another form.Word indices, binary bytes, hexadecimal text, and mixed-case formatting.

Encoding does not add entropy. Hashing is not encryption or public-key scalar multiplication, and a checksum is neither authentication nor a digital signature. HMAC is a keyed construction using a hash; PBKDF2 repeatedly applies its pseudorandom function to derive key material. These constructions are more than simply renaming a digest.

SHA-2 and Keccak/SHA-3

SHA-256 and SHA-512 belong to SHA-2. Keccak uses a different, sponge-based design and became the basis of NIST's SHA-3 standard in 2015. Ethereum Keccak-256 and NIST SHA3-256 are different functions: their domain-separation/padding conventions differ. Both return 256 bits, but identical inputs generally yield different digests; SHA3-256 cannot be substituted for Ethereum Keccak-256. FIPS 202 · Keccak specification summary

Each entropy string determines exactly one checksum among 2^CS possibilities. Therefore 2^ENT / 2^(ENT + CS) = 2^(-CS) of all word-index sequences are valid. This is an exact combinatorial fraction, not a probability of breaking a wallet. Checksum bits detect some errors; they supply no independent entropy.

Digits have no case: digits + uppercase + lowercase = 40, while uppercase + lowercase = alphabetic characters. Only the letter positions can carry case information.

For independent, uniformly distributed hexadecimal characters, let L count the letters (six of sixteen symbols):

L ∼ Binomial(40, 6/16)
E[L] = 15

In an idealized random-case acceptance model, the hash-dependent capitalization bits are independent fair bits, so acceptance conditional on L has probability 2−L. Averaging over L gives:

P(accepted) = E[2−L] = (13/16)40 ≈ 0.0247%

The 15 average check positions vary between addresses, so averaging acceptance differs from substituting the mean: 2−15 ≈ 0.00305% underestimates it. The formula is exact under this model and agrees with EIP-55's reported approximate rate; it is not a guarantee for every transcription error. Selected fixtures are descriptive examples, not a representative statistical sample.

What the results establish

Twelve words encode 128 initial entropy bits; twenty-four encode 256. Expanding either into a 512-bit seed does not create independent randomness. With the same mnemonic, passphrase, and path, derivation reproduces the same key material; different paths generally produce different keys, not fresh random draws.

Scalar multiplication is deterministic. Its security relies on the assumed difficulty of the elliptic-curve discrete logarithm problem with appropriate parameters, not random-looking output. Hashes are designed for preimage and collision resistance, with avalanche-like behavior; these two experiments do not test Keccak's uniformity or avalanche properties. A 160-bit address has an output space of 2^160, even though its source digest has 256 bits.

The layout values are exact specification-based calculations; the case counts measure chosen examples. Expected cryptographic properties and computational-security claims are separate. EIP-55 capitalization adds neither key entropy nor address bits, and a valid checksum proves neither ownership nor control of a private key.

The assignment's approximate 2001 date for SHA-2 is distinguished here from NIST's formal August 2002 publication of FIPS 180-2. The BIP years follow their specification dates; these technologies solve different problems rather than forming a sequence of replacements.

Why several techniques?

BIP-39 makes secure randomness recoverable as words and derives a seed. BIP-32 expands seed material into a reproducible key tree; BIP-44 gives that tree a consistent organization. secp256k1 connects private and public keys and supports signatures. Keccak-256 produces an address from public-key data, while EIP-55 adds transcription-error detection through capitalization.

No single algorithm supplies all these roles. The pipeline combines randomness, deterministic derivation, public-key cryptography, hashing, and encoding/error detection. Correct inputs, paths, byte serialization, and hash variants matter at every boundary. Compatible wallet applications may expose these steps differently; no wallet software is required for the two calculations on this page.
