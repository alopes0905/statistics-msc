01 Encryption and decryption

Homework 1.1 used y² = x³ + 7 over F17. Here the arithmetic uses authentic secp256k1: the same curve equation over the much larger prime field with p = 2256 − 232 − 977, the generator G and prime order n from SEC 2, §2.4.1, and cofactor 1. Coordinates and scalars use exact JavaScript BigInt arithmetic.

Point multiplication establishes a shared secret. It does not directly encrypt text. This educational ECIES-like hybrid combines ECDH, HKDF-SHA-256, and AES-256-GCM. The receiver deliberately uses 1 ≤ d ≤ K, with defaults d = 37 and K = 256. This tiny private-key range makes the complete demonstration insecure.

  1. Receiver: keep private scalar d and publish Q = dG. Here d is exposed for teaching.
  2. Sender: encode the message as UTF-8; securely sample a fresh ephemeral r ∈ {1, …, n − 1}; compute R = rG and S = rQ.
  3. Encrypt: HKDF derives a 256-bit AES key from S, a fresh 32-byte salt, and a versioned context binding R and Q. AES-GCM uses a fresh 12-byte IV and a 16-byte authentication tag.
  4. Transmit: version, R, salt, IV, and authenticated ciphertext. Each point is 04 || x[32 bytes] || y[32 bytes]; the ephemeral secret r is never included.
  5. Decrypt: validate the payload and R, compute S′ = dR, derive the same AES key, verify the tag, and decode UTF-8. A wrong key or altered authenticated data is rejected.

rQ = r(dG) = d(rG) = dR explains the shared secret. The protocol label, both public keys, salt, and IV are bound through key derivation and authenticated data. AES-GCM detects tampering under the derived key; it does not establish the sender’s identity, since anyone with Q can encrypt.

At most 4,096 UTF-8 bytes. Empty text, spaces, punctuation, and well-formed Unicode are supported by the hybrid scheme. Changing this message clears both demonstrations.

02 Comparing the schemes

Caesar is a symmetric substitution cipher. The hybrid uses a public/private key pair to establish the symmetric key that actually encrypts the message. The following properties describe these particular implementations.

For Caesar, a frequency histogram is shifted rather than flattened. The hybrid’s ciphertext should not be judged secure merely because it looks irregular: key-space analysis already breaks this configuration. AES-GCM’s tag protects integrity under its key, while ECDH and HKDF establish that key.

03 Statistical Caesar cryptanalysis

The English model is learned from Lewis Carroll’s Alice’s Adventures in Wonderland; evaluation uses the distinct book Through the Looking-Glass. Both are public-domain texts in the USA, obtained from documented GITenberg archives and bundled locally with their notices. The publisher’s header and license footer are excluded from counting. For each letter i, count its training occurrences and divide by the training total: pi = counti / Ntrain. Case is folded only for ASCII letters. This model uses single-letter frequencies and ignores word order and punctuation.

Rank the candidate plaintexts

Decrypt the ciphertext under each k from 0 to 25, count the candidate’s N letters, and compare observed counts Oi with Ei = Npi. The key with the smallest Pearson score is the closest fit:

χ²(k) = Σi=AZ (Oi(k) − Ei)² / Ei

This is a ranking score, not a confidence percentage or a formal goodness-of-fit test. In short samples, several expected counts are small; meaningful ranking can still fail. Scores equal within floating-point tolerance are flagged as ties and ordered by key; no-letter inputs provide no evidence.

Different lengths reuse the same held-out book. The two books share an author and vocabulary; this is a reproducible within-author experiment, not an estimate for all English.

Short windows fluctuate and may cut across words. Longer windows usually approximate the reference distribution more closely, but accuracy need not increase monotonically or reach 100% on another dataset. Language mismatch, unusual vocabulary, and repetitive text can mislead even long samples. Nonletters contribute no evidence to this model. A large chi-square gap alone is not a calibrated guarantee.

Exhaustive search versus statistical scoring

Exhaustive search lists all 26 possible decryptions but needs a selection criterion. Frequency analysis supplies an automatic language-based ranking; it does not reduce the already tiny key space. N-gram scoring could also use letter pairs or triples to distinguish some short candidates, but is not implemented here. See Handbook of Applied Cryptography, §7.3 for classical substitution ciphers and cryptanalysis.

04 Restricted-key ECC attack

The attacker knows G, public Q, the bound K, and the intercepted payload. Enumerating G, 2G, …, KG by repeated addition finds the candidate d′ for which d′G = Q. This exact public-point equality recovers d without language statistics or known plaintext. The recovered key then computes dR and authenticates/decrypts the actual ciphertext from Section 01.

Why properly configured ECC is different

For a uniformly generated secp256k1 private key, 1 ≤ d < n, where n = 0xfffffffffffffffffffffffffffffffebaaedce6af48a03bbfd25e8cd0364141. This gives approximately 2256 possible scalars. Exhaustive search is of that order, but it is not the best generic discrete-logarithm attack: Pollard’s rho takes expected work proportional to √n, approximately 2128 group operations, under its random-walk model (HAC, §3.6.3). Both scales are infeasible with conventional resources. A 256-bit scalar domain therefore corresponds to about 128-bit generic classical group security, not 256-bit security for every attack.

Caesar recovery exploits language redundancy and scores candidate plaintexts. This ECC attack exploits the small receiver-key interval and compares public points, so it works equally for English, Unicode, or empty messages. The field remains 256-bit secp256k1 throughout; the range of d is the weakness.

Other constructions can fail through predictable or reused ephemeral randomness, weak random generators, invalid public points, missing authentication, or implementation mistakes. These are distinct from the demonstrated small-key attack. This demo validates points and uses secure ephemeral randomness and authenticated encryption, but its exposed keys, restricted range, and variable-time educational arithmetic remain unsuitable for real secrets. Full-system security also depends on the protocol and its implementation.

Conclusions and verification

Correct round trips alone do not establish security. Caesar preserves exploitable language patterns; a sound-looking hybrid still fails when its private-key domain is tiny. The tests compare curve arithmetic and shared secrets with Node/OpenSSL, check authenticated encryption against independent Node primitives, verify all Caesar shifts, and recompute the corpus results. No blockchain connection, wallet, external runtime library, or remote analysis service is used.
